1. PROJECT OVERVIEW
================================================================================

This is a full-stack, AI-powered customer feedback analysis and action item
tracking system. It enables teams to:

  - Submit customer feedback entries through a rich-text form
  - Automatically analyze feedback using Google Gemini AI (with OpenAI fallback)
  - View AI-generated summaries, sentiment analysis, classifications,
    feature requests, and actionable insights
  - Track action items on a Kanban board or table view
  - Write, edit, and delete internal notes for each feedback entry
  - Filter and search across all feedback records
  - Authenticate using cookie-based JWT sessions

The application is structured as a monorepo with two independent applications:
  - Backend/  → Express.js REST API (TypeScript)
  - Frontend/ → Next.js 15 web application (App Router, TypeScript)

Both are started concurrently from the root using the "concurrently" package.

---------------------------------------------------------------------------
Variable                         | Description
---------------------------------------------------------------------------
PORT                             | Server port (default: 4000)
JWT_SECRET                       | Secret key for signing JWT tokens
DATABASE_URL                     | PostgreSQL connection string (Neon)
GOOGLE_GENERATIVE_AI_API_KEY     | Primary Google Gemini API key
GEMINI_FALL_BACK_KEY             | Fallback Gemini API key
GEMINI_API_KEYS                  | Comma-separated list of rotation keys
OPENAI_API_KEY                   | OpenAI API key (last-resort fallback)

The config.ts file uses Zod to validate these at startup:
  - PORT defaults to "4000" if not specified
  - JWT_SECRET is required (min 1 character)
  - DATABASE_URL is required and must be a valid URL
  - All AI keys are optional (the system degrades gracefully)

If validation fails, the process exits with error details.

FRONTEND (.env.local file in Frontend/ directory):
---------------------------------------------------------------------------
Variable                         | Description
---------------------------------------------------------------------------
NEXT_PUBLIC_API_URL              | Backend API base URL (e.g. http://localhost:4000/api)
---------------------------------------------------------------------------

The Axios instance also dynamically detects the hostname at runtime. If
accessing from a LAN IP or custom domain (e.g. mobile testing), it
auto-constructs the backend URL as: {protocol}//{hostname}:4000/api.

5. BACKEND — DEEP DIVE
================================================================================


5.1  ENTRY POINT — Backend/src/index.ts
---------------------------------------

This is the main file that boots the Express server.

What it does:
  1. Imports the validated environment config (env)
  2. Creates an Express application instance
  3. Configures global middleware:
     - CORS: Allows all origins with credentials (cookies). Methods: GET, POST,
       PUT, DELETE, OPTIONS. Headers: Content-Type, Authorization.
     - JSON body parser: express.json()
     - Cookie parser: cookieParser()
  4. Mounts route groups:
     - /api/auth     → auth routes (register, login, logout, me, users)
     - /api/feedback → feedback routes (CRUD + notes)
     - /api          → action item routes (CRUD + approve/reject)
  5. Adds a /health endpoint returning { status: "ok", time }
  6. Starts listening on the configured PORT
  7. Tests the database connection with "SELECT 1" query on startup

Key learning:
  - The CORS origin callback always allows (callback(null, true)). This is
    permissive and works for development. In production, you'd restrict origins.
  - The database test query happens AFTER the server starts listening, so the
    server is available even if the DB test fails.


5.2  CONFIGURATION — Backend/src/config.ts
------------------------------------------

This file handles environment variable loading and validation.

How it works:
  1. Calls dotenv.config() to load Backend/.env
  2. Defines a Zod schema (envSchema) for all expected variables
  3. Uses safeParse(process.env) to validate
  4. If validation fails: logs formatted errors and exits with code 1
  5. If validation succeeds: exports the typed `env` object

Key learning:
  - Using Zod for env validation ensures the app fails fast with clear error
    messages instead of cryptic runtime errors when keys are missing.
  - The parsed `env` object is fully typed, so TypeScript catches any typos
    when accessing env.PORT, env.JWT_SECRET, etc.

5.3.3  Migrations — Backend/src/db/migrate.ts + drizzle.config.ts

  drizzle.config.ts:
    - Tells drizzle-kit where to find the schema (./src/db/schema.ts)
    - Where to output migrations (./src/db/migrations)
    - Dialect: PostgreSQL
    - Reads DATABASE_URL from .env for connecting

  migrate.ts:
    - A standalone script that runs all pending migrations
    - Uses drizzle-orm/neon-http/migrator
    - Run via: npm run db:migrate (which calls tsx src/db/migrate.ts)

  Migration workflow:
    1. Edit schema.ts (add/change tables or columns)
    2. Run "npm run db:generate" → creates new SQL migration files
    3. Run "npm run db:migrate" → applies migrations to the database


5.4  MIDDLEWARE
--------------

5.4.1  Authentication Middleware — Backend/src/middleware/auth.ts

  Exports:
    - AuthenticatedRequest interface (extends Express Request with userId?: string)
    - authenticateToken function

  How it works:
    1. Reads the "token" from req.cookies (set during login/register)
    2. If no token → responds 401 "Access token required"
    3. Verifies the token using jwt.verify() with JWT_SECRET
    4. If invalid/expired → responds 403 "Invalid or expired token"
    5. If valid → extracts decoded.userId, sets req.userId, calls next()

  Key learning:
    - The token is stored in an HTTP-only cookie (not localStorage), which
      prevents XSS attacks from stealing the token.
    - All protected routes use this middleware, so req.userId is always available
      in controller functions after authentication succeeds.
    - The middleware is applied per-route-group (e.g., router.use(authenticateToken))
      rather than globally, so auth routes like /register and /login are public.


5.5  CONTROLLERS
----------------

5.5.1  Auth Controller — Backend/src/controllers/auth.controller.ts

  Exports 5 functions:

  a) registerUser(req, res)
     - Validates body with Zod: { username (min 3), email (valid), password (min 6) }
     - Checks if username already exists in DB
     - Hashes password with bcrypt (10 salt rounds)
     - Inserts new user into "users" table
     - Signs a JWT token (expires in 7 days)
     - Sets HTTP-only cookie named "token"
     - Returns 201 with user data (id, username, email)

  b) loginUser(req, res)
     - Validates body with Zod: { username (min 3), password (min 6) }
     - Looks up user by username
     - Compares password hash using bcrypt.compare()
     - Signs a JWT token (7 day expiry)
     - Sets HTTP-only cookie
     - Returns 200 with user data

  c) logoutUser(req, res)
     - Clears the "token" cookie
     - Returns 200 "Logged out successfully"

  d) getUserProfile(req, res)
     - Requires authentication (uses AuthenticatedRequest)
     - Looks up user by req.userId
     - Returns { id, username, email }

  e) getAllUsers(req, res)
     - Requires authentication
     - Returns all users with only { id, username, email } columns

  Key learning:
    - Cookie settings: httpOnly=true, secure=true in production, sameSite="lax",
      maxAge=7 days. This balance of security settings prevents CSRF while
      allowing same-site navigation.
    - Zod validation errors return the first error message as a 400 response.


5.5.2  Feedback Controller — Backend/src/controllers/feedback.controller.ts

  Exports 5 functions:

  a) createFeedback(req, res)
     - Validates body with feedbackSchema (Zod)
     - Sanitizes content using cleanContent() — strips HTML, Markdown, entities
     - Calls analyzeFeedback() from AI service (the big AI call)
     - Extracts AI-suggested action items and formats them with IDs
     - Inserts feedback record with all AI fields populated
     - Returns 201 with the new record

  b) getFeedbackList(req, res)
     - Accepts query params: search, category, source, status, limit
     - Builds dynamic SQL conditions:
       * Always filters by userId and isDeleted=false
       * Optionally adds category, source, status exact matches
       * Optionally adds search with LIKE on title, customerName, content
     - Orders by createdAt DESC
     - Supports optional limit parameter
     - Returns array of matching feedback records

  c) getFeedbackDetails(req, res)
     - Takes :id from URL params
     - Finds feedback by id + userId + isDeleted=false
     - Returns 404 if not found
     - Returns the full feedback record

  d) updateFeedback(req, res)
     - Takes :id from URL params
     - Uses partial() Zod schema (all fields optional)
     - Verifies ownership (userId match) and that record is not deleted
     - If content or category changed → re-runs AI analysis
     - Updates the record with new data + AI results
     - Returns updated record

  e) deleteFeedback(req, res)
     - Takes :id from URL params
     - Verifies ownership
     - Performs soft delete (isDeleted=true) on:
       * The feedback record itself
       * All associated action_items (same feedbackId)
       * All associated internal_notes (same feedbackId)
     - This is a CASCADING SOFT DELETE

  Helper: cleanContent(text)
     - Strips HTML tags with regex
     - Unescapes HTML entities (&nbsp;, &lt;, &gt;, &amp;, etc.)
     - Strips Markdown syntax (headings, bold, italic, links, code, quotes)
     - Normalizes whitespace and double newlines
     - Returns clean plain text

  Key learning:
    - AI analysis is triggered synchronously during create and update. This means
      the API response is delayed until the AI completes (can take several seconds).
    - The feedbackSchema validates a comprehensive set of fields including enums
      for source, category, and status.
    - The AI-suggested action items are stored as JSONB in the feedback record,
      NOT as actual action_items table rows. They become real rows only when
      the user explicitly approves them.


5.5.3  Action Controller — Backend/src/controllers/action.controller.ts

  Exports 7 functions:

  a) getAllActionItems(req, res)
     - INNER JOINs actionItems with feedback to get feedbackTitle
     - Filters by userId (via feedback ownership), isDeleted=false on both tables
     - Returns all action items across all user feedback entries

  b) getActionItems(req, res)
     - Takes :feedbackId from params
     - Verifies feedback ownership first
     - Returns action items for that specific feedback

  c) createActionItem(req, res)
     - Validates body with actionItemSchema (description, owner, dueDate, priority, status)
     - Verifies feedback ownership
     - Inserts new action item

  d) updateActionItem(req, res)
     - Takes :id from params
     - Uses partial schema (all fields optional)
     - Finds existing item, verifies it's not deleted
     - Verifies parent feedback ownership
     - Updates the action item

  e) deleteActionItem(req, res)
     - Takes :id from params
     - Verifies item exists and parent feedback ownership
     - Soft deletes (isDeleted=true)

  f) approveActionItemSuggestion(req, res)
     - Takes :feedbackId from params and { id, description, owner, priority, dueDate } from body
     - Finds the AI suggestion in feedback.aiActionItems by matching the suggestion id
     - Creates a real action_items table row from the suggestion
     - Removes the approved suggestion from the feedback's aiActionItems JSONB array
     - Returns the new action item

  g) rejectActionItemSuggestion(req, res)
     - Takes :feedbackId from params and { id } from body
     - Removes the rejected suggestion from feedback.aiActionItems JSONB array
     - Does NOT create any action_items row

  Key learning:
    - The approve/reject workflow converts AI suggestions (stored as JSONB)
      into real database records. This is a deliberate "human-in-the-loop"
      design — AI suggests, human approves.
    - The dueDate for approved items is calculated from daysToComplete if
      not explicitly provided.


5.5.4  Note Controller — Backend/src/controllers/note.controller.ts

  Exports 4 functions:

  a) createNote(req, res)
     - Validates body: { content (min 1 char) }
     - Verifies feedback ownership via helper function
     - Looks up the user to get their username
     - Inserts note with createdBy = user's username (not ID)
     - Returns the new note

  b) getNotes(req, res)
     - Takes :feedbackId from params
     - Verifies feedback ownership
     - Returns all non-deleted notes, ordered by createdAt ASC

  c) updateNote(req, res)
     - Takes :id from params
     - Validates body: { content }
     - Finds the note, verifies it's not deleted
     - Verifies parent feedback ownership
     - Updates content and updatedAt

  d) deleteNote(req, res)
     - Takes :id from params
     - Finds the note, verifies parent feedback ownership
     - Soft deletes

  Helper: verifyFeedbackOwner(feedbackId, userId)
     - Checks if a feedback record exists that matches both the feedbackId
       and the userId, and is not deleted
     - Returns boolean

  Key learning:
    - Notes store the creator's username in createdBy, not their user ID.
      This means if a username changes, old notes won't reflect the new name.
    - All note operations first verify feedback ownership, ensuring users can
      only interact with notes on their own feedback entries.

5.7  SERVICES

5.7.1  AI Service — Backend/src/services/ai.ts

  This is the most complex file in the backend. It handles the AI analysis
  of customer feedback using a multi-provider fallback strategy.

  SCHEMAS DEFINED:

    sentimentAnalysisSchema:
      - overallTone: "Positive" | "Neutral" | "Concerned" | "Heated"
      - score: number (0-100, positivity score)
      - breakdown: { positive, neutral, concerned, heated } (percentages)

    featureRequestSchema:
      - description: string
      - reason: string
      - impact: string
      - priority: "Low" | "Medium" | "High" | "Critical"
      - status: "Requested" | "Under Review" | "Planned" | "Deferred"

    aiActionItemSchema:
      - description: string
      - owner: string (suggested team/person)
      - priority: "Low" | "Medium" | "High"
      - daysToComplete: number

    aiAnalysisResultSchema (the master schema):
      - summary: { mainConcern, importantDetails, expectations, impact, suggestedNextSteps }
      - classification: { category, feedbackType, sentiment, priority, productArea }
      - sentimentAnalysis: (sentimentAnalysisSchema)
      - aiFeatureRequests: array of featureRequestSchema
      - aiActionItems: array of aiActionItemSchema
      - insights: array of strings

  MAIN FUNCTION: analyzeFeedback(content, userCategory) → AIAnalysisResult

    This function uses Vercel AI SDK's generateObject() to get structured JSON
    output from AI models. It follows a 4-tier fallback strategy:

    TIER 1: Primary Google Key (GOOGLE_GENERATIVE_AI_API_KEY)
      → Uses gemini-3.5-flash-lite model
      → If succeeds, returns immediately

    TIER 2: Key Rotation Policy (GEMINI_API_KEYS — comma-separated)
      → Tries each key sequentially
      → Filters out the primary key to avoid duplicates
      → If any succeeds, returns immediately

    TIER 3: Fallback Gemini Key (GEMINI_FALL_BACK_KEY)
      → Single dedicated fallback key
      → If this fails, tries OpenAI

    TIER 3.5: OpenAI Fallback (OPENAI_API_KEY)
      → Uses gpt-4o-mini model
      → Only attempted if OPENAI_API_KEY is configured

    TIER 4: Heuristic Generator (hardcoded fallback)
      → Returns a static, neutral analysis result
      → Includes a warning that all API keys failed
      → Suggests checking .env configuration

  Helper: getRotationPolicyApiKeys()
    - Parses GEMINI_API_KEYS env var (comma-separated)
    - Cleans quotes and whitespace from each key
    - De-duplicates using Set

  Helper: toPlainText(text)
    - Same HTML/Markdown stripping as cleanContent in feedback controller
    - Used to sanitize content before sending to AI

  Key learning:
    - The generateObject() function from Vercel AI SDK ensures the AI returns
      structured data matching the Zod schema. This is much more reliable than
      parsing free-text AI responses.
    - The fallback chain makes the system resilient — even if all Gemini keys
      are rate-limited, it tries OpenAI, and even if that fails, it returns a
      sensible hardcoded result so the user experience never breaks.
    - Masked API keys are logged for debugging (first 4 + last 4 chars only).

9. AUTHENTICATION FLOW (END-TO-END)
================================================================================

  REGISTRATION FLOW:

    Frontend                              Backend
    ─────────                             ───────
    1. User fills signup form
       (username, email, password,
        confirmPassword)
    2. Zod validation on frontend
       (signupSchema with password match)
    3. POST /api/auth/register  ────────→ 4. Validate with registerSchema (Zod)
                                          5. Check username uniqueness in DB
                                          6. Hash password (bcrypt, 10 rounds)
                                          7. Insert user into "users" table
                                          8. Sign JWT { userId } (7 day expiry)
                                          9. Set HTTP-only cookie "token"
    10. Receive user data        ←─────── 10. Return 201 { user: { id, username, email } }
    11. Set user in AuthContext
    12. Sync to Zustand store
    13. Redirect to /chat

  LOGIN FLOW:

    Frontend                              Backend
    ─────────                             ───────
    1. User fills login form
       (username, password)
    2. Zod validation (authSchema)
    3. POST /api/auth/login     ────────→ 4. Validate with authSchema (Zod)
                                          5. Find user by username
                                          6. Compare password with bcrypt
                                          7. Sign JWT { userId } (7 day expiry)
                                          8. Set HTTP-only cookie "token"
    9. Receive user data         ←─────── 9. Return 200 { user: { id, username, email } }
    10. Set user in AuthContext
    11. Sync to Zustand store
    12. Redirect to /chat

  SESSION CHECK (On every app load):

    Frontend                              Backend
    ─────────                             ───────
    1. AuthContext mounts
    2. GET /api/auth/me         ────────→ 3. authenticateToken middleware
       (cookie sent automatically)        4. Read "token" from cookies
                                          5. Verify JWT → extract userId
                                          6. Look up user in DB
    7. Receive user data         ←─────── 7. Return { id, username, email }
       OR set user=null if 401/403

  LOGOUT FLOW:

    Frontend                              Backend
    ─────────                             ───────
    1. User clicks logout
    2. POST /api/auth/logout    ────────→ 3. Clear "token" cookie
    4. Set user=null in context  ←─────── 4. Return 200
    5. Clear Zustand store
    6. Redirect to /login

  ROUTE PROTECTION:
    - AuthContext has a useEffect that watches user state and pathname
    - If user is null and not on /login or /signup → force redirect to /login
    - If user exists and on /login or /signup → redirect to /chat

12. KEY DESIGN PATTERNS USED
================================================================================

  1. MONOREPO PATTERN
     - Backend/ and Frontend/ in one repository
     - Root package.json runs both concurrently
     - Shared nothing architecture (each has own dependencies)

  2. MVC PATTERN (Backend)
     - Models: db/schema.ts (Drizzle table definitions)
     - Views: N/A (REST API returns JSON)
     - Controllers: controllers/*.ts (business logic)
     - Routes: routes/*.ts (URL mapping)

  3. MIDDLEWARE PATTERN
     - Express middleware chain for auth
     - Applied per-route-group, not globally

  4. REPOSITORY PATTERN (via ORM)
     - Drizzle ORM abstracts SQL queries
     - Controllers use db.query.* and db.insert/update for data access

  5. SOFT DELETE PATTERN
     - isDeleted flag instead of hard deletes
     - All queries filter by isDeleted=false
     - Cascade soft-delete for parent→child relationships

  6. FALLBACK/RETRY PATTERN (AI Service)
     - Multi-tier fallback: Primary → Rotation → Fallback → OpenAI → Heuristic
     - System never crashes due to AI failure

  7. CONTEXT + STORE PATTERN (Frontend)
     - React Context for auth (provides functions + state)
     - Zustand for lightweight global state (user info)
     - Components choose which to consume based on needs

  8. CONTAINER/COMPONENT PATTERN (Frontend)
     - Pages (app/chat/*.tsx) are containers — fetch data, manage state
     - Components (components/*.tsx) are presentational — receive props, render UI

  9. SCHEMA-FIRST VALIDATION
     - Zod schemas defined once, used for both validation and TypeScript types
     - Backend and frontend both use Zod (schemas are duplicated but consistent)

  10. HUMAN-IN-THE-LOOP AI PATTERN
     - AI generates suggestions (stored as JSONB)
     - User explicitly approves or rejects
     - Approved items become real database records

13. HOW TO RUN THE PROJECT
================================================================================

  PREREQUISITES:
    - Node.js v18 or higher
    - A Neon PostgreSQL database instance
    - Google Gemini API key(s) and/or OpenAI API key

  STEP 1: Clone and install root dependencies
    cd AI-Feedback
    npm install

  STEP 2: Set up Backend environment
    - Create/edit Backend/.env with:
      PORT=4000
      JWT_SECRET=your-secret-key
      DATABASE_URL=postgresql://user:pass@host/dbname?sslmode=require
      GOOGLE_GENERATIVE_AI_API_KEY=your-primary-gemini-key
      GEMINI_FALL_BACK_KEY=your-fallback-key (optional)
      GEMINI_API_KEYS=key1,key2,key3 (optional, for rotation)
      OPENAI_API_KEY=your-openai-key (optional fallback)

  STEP 3: Install Backend dependencies
    cd Backend
    npm install

  STEP 4: Generate and run database migrations
    npm run db:generate
    npm run db:migrate

  STEP 5: Install Frontend dependencies
    cd ../Frontend
    npm install

  STEP 6: Set up Frontend environment (optional)
    - Create Frontend/.env.local with:
      NEXT_PUBLIC_API_URL=http://localhost:4000/api

  STEP 7: Run both servers from root
    cd ..
    npm run dev

    This starts:
      - Backend on http://localhost:4000
      - Frontend on http://localhost:3000

  ALTERNATIVE: Run individually
    Terminal 1: cd Backend && npm run dev
    Terminal 2: cd Frontend && npm run dev

  NPM SCRIPTS REFERENCE:

    Root:
      npm run dev          → Runs both Backend and Frontend concurrently

    Backend:
      npm run dev          → tsx watch src/index.ts (hot-reload dev server)
      npm run build        → tsc (compile TypeScript)
      npm start            → node dist/index.js (run compiled)
      npm run db:generate  → drizzle-kit generate (create migration files)
      npm run db:migrate   → tsx src/db/migrate.ts (apply migrations)

    Frontend:
      npm run dev          → next dev (development server with HMR)
      npm run build        → next build (production build)
      npm start            → next start (serve production build)
      npm run lint         → eslint (code quality check)

14. KNOWN LIMITATIONS
================================================================================

  1. AI LATENCY: The AI analysis runs synchronously during feedback create/update.
     Users must wait several seconds for the API response. There is no background
     job queue or async processing.

  2. RICH TEXT TRUNCATION: HTML content inside table listings is truncated to
     plain text summaries for readability. Full rich text only shows in detail views.

  3. ONLINE DEPENDENCY: Requires internet for Neon PostgreSQL and Gemini/OpenAI APIs.
     The app cannot run fully offline.

  4. NO PAGINATION: Feedback listing returns all records matching the filter.
     For large datasets, this could become slow. The only limit mechanism is the
     optional "limit" query parameter.

  5. NO RBAC: All authenticated users have equal permissions. No admin, manager,
     or agent role distinctions.

  6. USERNAME IMMUTABILITY: Notes store createdBy as username string, not FK.
     If username changes, historical notes won't reflect the updated name.

  7. NO RATE LIMITING: API has no rate limiting middleware. Susceptible to abuse
     in production without additional infrastructure.

  8. NO TESTS: No unit tests, integration tests, or e2e tests exist.
     Verification is manual only.

  9. CORS WIDE OPEN: The CORS configuration allows all origins. In production,
     this should be restricted to the frontend domain only.

  10. DUPLICATE VALIDATION: Zod schemas are defined separately in both Backend
      and Frontend. Changes must be synchronized manually.
